# LLM Tokenization Analyzer

A full-stack developer tool for understanding and comparing how NLP tokenizers convert human text into tokens and token IDs — the actual units that language models read, instead of raw characters or words.

**Tech stack:** React, TypeScript, FastAPI, Python, Hugging Face Transformers, GPT-2, BERT Base Cased

---

## Problem statement

Everyone talks about "tokens" when discussing LLMs — context limits, API pricing, rate limits — but very few people have actually seen what tokenization does to their own text. This project makes that process visible and comparable: type anything, pick a tokenizer, and see exactly how it gets split up, what IDs it maps to, and what that means for context usage and cost.

## Why tokenization matters

- Models don't read letters or words — they read a fixed vocabulary of tokens, and every input is chopped up (usually via subword algorithms like BPE or WordPiece) to fit that vocabulary.
- Token count, not character count, determines how much of a model's context window a prompt uses and how much an API call costs.
- Different tokenizers segment the *same* text differently — GPT-2's byte-level BPE and BERT's WordPiece make different tradeoffs, especially on multilingual or unusual text — which is why "the same sentence" can cost different amounts of context depending on the model.

## Architecture

```
User
 │
 ▼
React + TypeScript (Dashboard)
 │  fetch('/api/...')
 ▼
FastAPI REST API  (routes/: tokenize, analysis, compare — thin, HTTP-only)
 │
 ▼
Service layer
 ├─ TokenizerService  → Hugging Face AutoTokenizer (GPT-2 / BERT Base Cased), cached in-memory
 ├─ AnalysisService   → character/word/token counts, ratios, context utilization
 └─ CostService       → configurable token-cost estimate
 │
 ▼
JSON response → rendered by React dashboard (token viewer, stats, comparison, context bar, cost card)
```

Design principles this codebase follows:
- **Thin routes, fat services.** `app/api/routes/*.py` only handles HTTP concerns; all logic lives in `app/services/`.
- **One tokenizer instance per model, reused across requests** (`TokenizerService` caches loaded tokenizers behind a lock, so concurrent cold-start requests can't trigger duplicate loads).
- **No fabricated output.** Every token, token ID, and count in this app comes from a real Hugging Face tokenizer call — nothing is hard-coded or simulated.
- **Config, not hard-coding.** Supported models, default context windows, and pricing are one entry in `app/config.py` — adding a third tokenizer later is a one-line change plus a checkpoint that `AutoTokenizer` supports.

## Features

- Real GPT-2 and BERT Base Cased tokenization, side by side or individually
- Per-token inspection: text, token ID, and position, with hover/click detail
- Text, word, character, and unique-token statistics
- GPT-2 vs BERT comparison table + bar chart (characters/token, tokens/word, token counts)
- Multilingual sample presets (English, Hindi, Telugu, Tamil, Japanese, Arabic)
- Configurable context-window utilization with a warning/critical/over-limit indicator
- Configurable token-cost estimator (you set the price — this app has no opinion on real provider pricing)
- Health check, loading states, validation errors, and API-down states handled explicitly

## Non-goals

This is a tokenization analyzer, not a chatbot, not a training platform, and not a RAG/vector-database project. It doesn't claim that token count alone determines model quality, or that GPT-2/BERT tokenization behavior generalizes to every modern LLM — it's a concrete, correct example of *how* tokenization works, not a universal benchmark.

## API documentation

All routes are under `/api`. Full interactive docs are auto-generated by FastAPI at `http://localhost:8000/docs` once the backend is running.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Confirm the backend is running |
| GET | `/api/models` | List supported tokenizers |
| POST | `/api/tokenize` | Tokenize text with one or more models, returning tokens/IDs/positions |
| POST | `/api/analyze` | Character/word/token statistics per model |
| POST | `/api/compare` | Same as analyze, plus shared character/word counts for side-by-side comparison |
| POST | `/api/context-analysis` | Context-window utilization for a given token count/text and configured max |
| POST | `/api/cost-estimate` | `(token_count / 1000) × price_per_1000_tokens` |

Errors always come back as `{"detail": "..."}` with an appropriate 4xx/5xx status — no stack traces are ever sent to the client.

## Setup

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The first time you tokenize with a given model, the backend downloads that tokenizer from the Hugging Face Hub and caches it locally — this requires outbound internet access to `huggingface.co` on first run only. After that, the tokenizer is cached in memory for the life of the process (and on disk by `huggingface_hub`'s own cache for future restarts).

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Vite proxies `/api` to `http://localhost:8000` in dev (see `vite.config.ts`), so just open the printed local URL (typically `http://localhost:5173`) once both servers are running.

## Testing

```bash
cd backend
pytest
```

Test coverage includes:
- **Tokenizer service** — real tokenizer output, token/ID correspondence, caching, multilingual input
- **Analysis service** — character/word/token counts, ratios, empty/punctuation/unicode edge cases
- **Context service** — zero, normal, near-limit, at-limit, over-limit, and invalid-max cases
- **Cost service** — zero/normal/decimal pricing, negative-value rejection
- **API layer** — health, models, valid/invalid requests, malformed payloads, error responses

> Note: tests that exercise real tokenization need outbound access to `huggingface.co` the first time each tokenizer is loaded (to download `gpt2` / `bert-base-cased`). If you're running in a network-restricted sandbox, those specific tests will fail with a connection error until that host is reachable or the tokenizer is pre-cached — this is an environment/network constraint, not a bug in the code. Pure-logic tests (analysis, cost, validation) don't touch the network and pass regardless.

```bash
cd frontend
npm run build   # type-checks with tsc -b, then bundles with vite
```

## Example tokenization comparison

Run the app and try this yourself rather than trusting numbers in a README — token IDs depend on the exact installed tokenizer version, and this project's whole point is "don't take tokenization on faith." A good first comparison: type `"I love learning AI."`, select **Compare Both**, and look at:
- GPT-2 (byte-level BPE) will likely split off the leading space as part of each subword.
- BERT Base Cased (WordPiece) will add `[CLS]`/`[SEP]`-style special-token handling conventions and split differently around punctuation.

Try one of the built-in multilingual samples (e.g. Telugu or Japanese) afterward — you'll typically see a much higher tokens-per-word ratio than English, which is exactly the kind of thing this tool exists to make visible.
